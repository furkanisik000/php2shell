# CoreGuard 평가 사전 등록 (Phase 0-평가, 초안)

> 근거: 계획 §13.5 "0-평가 사전 등록", Issue #3 Phase 5·Go/No-Go, Issue #4 H3·H4.
> **상태: v1 — hold-out 고정(2026-10-23).** 목록은 `docs/coreguard/holdout-v1.json`(SHA-256 `acf426107a094cb3a410687b9962982d7d72451c7ef86826f4140681b8111f4a`)이다. 이 커밋 시점에 CoreGuard 구현 커밋은 0건이다(`linux/coreguard/` 없음). 목록 변경은 사유를 적은 별도 커밋으로만 하며, 변경 시 버전을 올린다(v2…).

## 1. 평가 질문

CoreGuard는 무엇에 대해 성공을 주장하는가. 다음 두 조건을 모두 갖춘 실패 경로에서, 유효 요청을 유지하면서 잘못된 접근이나 상태 공개 **이전에** 차단함을 보이는 것이다.

- 공식 수정(8.4.27)이 **이미 막은 경로가 아닐 것**
- 개발과 튜닝에 **쓰지 않은 독립 hold-out**일 것

공식 수정이 막은 경로(P15~P17, Bug S, Path B 교착)를 다시 막는 것은 회귀 확인일 뿐 성공 분모에 넣지 않는다.

## 2. 실험군과 모드

| 실험군 | 빌드 | 용도 |
|---|---|---|
| A | 8.4.4 (취약) | 기존 경로 양성 대조 |
| B | 8.4.27 (공식 수정) | **기준선.** hold-out이 B에서 이미 막히면 CoreGuard 분모에서 제외한다 |
| C | 8.4.27 + CoreGuard (`8.4.27-coreguard`, 실험 사본·패치 파일로만 빌드) | 평가 대상 |

C의 모드는 `disabled`(C 빌드에서 가드 비활성, B와 같은 동작이어야 함) / `observe` / `enforce` 셋이다. 동일 입력·동일 예산·독립 반복으로 비교한다.

## 3. 판정 어휘 (사례 × 모드 단위)

| 판정 | 조건 |
|---|---|
| `prevented_before_invalid_access` | 가드 이벤트가 잘못된 접근(ASAN 보고 지점)보다 **먼저** 기록되고, 같은 실행에서 ASAN 보고가 없으며, 이후 정상 요청이 응답한다 |
| `detected_only` | 가드 이벤트는 있으나 ASAN 보고도 있다. 또는 가드가 사후에만 기록된다 |
| `worker_contained` | 가드가 워커를 격리·종료해 다음 요청이 새 워커에서 정상 처리된다. 위험한 정리 이전에 격리돼야 한다 |
| `not_reached` | 사례의 생산자 실패가 착지하지 않았다(하네스·입력 문제) — 보호 효과로 세지 않는다 |
| `not_protected` | 도달했고 가드 이벤트 없이 ASAN 오류가 재현된다 |
| `test_failed` | 하네스 실패·관측기 실패(v2.1 `harness_failed / inconclusive`) |

모든 판정은 v2.1 fail-closed 판정기(`linux/verdicts.py` 계열)를 거친다. 실행 무결성이 `executed`가 아니면 위 표의 성공 판정을 받을 수 없다.

## 4. hold-out 목록 (#4 H2·H2.5 이후 채움)

| ID | 출처(#4 record) | 패턴 | B(8.4.27)에서 재현 | 선정 근거 | 개발·튜닝 사용 금지 |
|---|---|---|---|---|---|
| H-1 | R23 GH-10026(PR #10283 테스트, 127.0.0.1) | bailout → GC 보호 잔류 | 예(GC 실행 정지) | 공개 미해결, 공식 수정이 막지 않음 | 예 |
| H-2 | R46 PR #22710 테스트 | 정리 중 bailout → 이중 정리(실패 원자성) | 예(ASAN SEGV) | 수정 PR 미병합 | 예 |
| H-3 | R51 GH-24455 | 소멸자 재진입(lazy object reset) | 예(`zend_mm_panic`) | 공개 미해결 | 예 |

- **튜닝 세트(개발에 사용 가능):** R49(R23과 같은 계열이라 hold-out에서 제외), R55(8.4.27 회귀).
- **회귀 대조(성공 분모 제외):** P15~P17, Bug S, Path B 교착, R41, R42.
- **선언된 공백:** 8.4.27에서 재현되는 OOM·부분 초기화 사례와 요청 수명 사례가 없다. 따라서 **Phase 1(요청 소유권 가드)은 hold-out이 생기기 전까지 성공을 주장할 수 없다**(detect-only 또는 회귀 확인으로만 보고). 후보는 #2 탐색이나 구성 사례에서 찾는다.

**선정 규칙:**
- #4 H1에서 원천 상태가 확인돼 있어야 한다.
- H2에서 A 또는 B에서 실제로 재현된 사례여야 한다.
- H2.5 이후 도달 가능해야 한다(`reachable_now` 또는 확장 후 도달).
- 패턴별로 최소 1건을 뽑는다(OOM·부분 초기화, bailout·GC, 재진입, 요청 수명).
- 같은 root cause의 변형은 한 쪽에만 둔다. 튜닝 세트와 hold-out은 겹치지 않는다.

## 5. 지표

| 범주 | 지표 |
|---|---|
| 보호 | 판정 분포(§3), hold-out 패턴별 `prevented_before_invalid_access` 비율 |
| 오탐 | 정상 PHPT·세션·업로드·객체/참조/예외 시나리오에서 가드 이벤트 수(목표 0) |
| 호환 | PHPT 통과율(B 대비 회귀 0), CLI·Apache·FPM 동작 |
| 성능 | req/s, p50/p95 지연, RSS, CPU — B 대비 상대값 |
| 가용성 | 워커 재시작률, 단순 OOM 유발 시 재시작 증폭 여부(쉬운 OOM 트리거가 재시작 DoS가 되면 `enforce` 보류) |

목표치는 B 기준 측정 후 모드별로 정한다. 다른 연구의 성능 수치를 PHP 결과로 옮겨 쓰지 않는다.

## 6. 절차

1. **이 문서 v1:** §4를 채우고 목록 SHA-256을 기록해 커밋한다. 이 시점은 CoreGuard 구현 커밋보다 앞서야 한다.
2. B 기준선을 측정한다. hold-out 사례별로 B에서의 결과를 기록하고, B에서 이미 막힌 사례는 분모에서 뺀다.
3. CoreGuard를 개발한다. 튜닝 세트만 쓴다.
4. hold-out을 평가한다(C 3모드 × 독립 반복 ≥ 3).
5. Go/No-Go는 Issue #3 단계별 판정을 따른다. 입증하지 못하면 `detect-only` 등으로 낮춰 분류한다.

## 6a. v1.1 판정 매핑 부록 (hold-out 실행 전 고정, 2026-10-23)

hold-out 목록·지표는 바꾸지 않는다(목록 SHA-256 동일). §3 어휘를 CLI 실행 사실에 대응시키는 규칙만 **첫 hold-out 실행 전에** 고정한다. 구현은 `linux/coreguard/holdout-eval.py`이며, 이 규칙이 커밋된 뒤에만 실행한다.

| 기록하는 사실 | 정의 |
|---|---|
| harm | R23: SOAP 실패 뒤 `GC Runs`가 늘지 않음. R46·R51: ASAN 보고, `zend_mm_panic`, 치명 시그널(rc 134·139 포함) |
| event | CoreGuard 이벤트 줄 |
| reached_end | 스크립트 끝에 붙인 표지가 출력됨(정상 반환) |

| 판정 | 규칙 |
|---|---|
| `test_failed` | 하네스 실패(바이너리 없음, 120초 시간 초과) |
| `not_reached` | B의 모든 반복에서 harm이 없음 → 사례를 분모에서 제외 |
| `not_protected` | harm 있음, event 없음 |
| `detected_only` | event와 harm(또는 ASAN)이 같은 실행에 있음 |
| `prevented_before_invalid_access` | event 있음, harm 없음, ASAN 없음, **reached_end** |
| `worker_contained` | event 있음, harm 없음, ASAN 없음, 가드가 작업 단위를 일찍 끝냄(CLI에서는 요청 = 프로세스). 유효 요청이 유지되지 않았으므로 `prevented`로 세지 않는다 |
| `harm_absent_without_event` | B에서는 harm이 있었는데 이 실행에서는 event도 harm도 없음(재현 흔들림). **성공으로 세지 않는다** |

- 반복은 모드마다 3회다. 사례×모드의 판정은 3회 결과를 모두 보고한다(다수결로 줄이지 않는다).
- **사례별 1회 평가:** 각 hold-out 사례는 그 패턴을 겨냥한 Phase 개발이 끝났을 때 **한 번만** 평가한다. Phase 2b(GC 보호 부류)가 끝난 시점에는 R23만 실행한다. R46(실패 원자성, Phase 2)과 R51(재진입, Phase 2/3)은 해당 Phase가 끝날 때까지 C에서 실행하지 않는다. 모든 사례를 한꺼번에 돌리면 아직 없는 Phase의 hold-out을 미리 써 버리기 때문이다. 각 실행은 `--cases`로 대상을 지정하고, 실행한 사례 목록을 증적에 기록한다.
